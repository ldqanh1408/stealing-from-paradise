Define Problem — Bối cảnh & 5 thách thức cốt lõi

Từ mô hình Single-vendor chuyển sang Multi-vendor Marketplace, 6 vấn đề phân tán nảy sinh — gộp thành 5 nhóm trong bài trình bày này.

🏪Bối cảnh thực tế

Chuyển dịch sang Multi-vendor Marketplace (Shopee, Lazada, Amazon) tạo hiệu ứng mạng lưới nhưng đặt ra 4 thách thức:

  • Tải tăng đột biến: Flash Sale tập trung traffic vào vài SKU hot — dễ oversell, dễ sập DB.
  • Phân rã dữ liệu: Microservices có DB riêng → khó giữ transaction xuyên service.
  • Pháp lý: NĐ 101/2012 & NĐ 52/2024 cấp phép trung gian thanh toán — sàn tự giữ tiền là vi phạm.
  • AI Security: Prompt Injection có thể ép LLM tự gọi API hủy đơn / hoàn tiền.

🎯Mục tiêu nghiên cứu

Không xây CRUD e-commerce — mà thiết lập kiến trúc tham chiếu giải quyết 6 nhóm bài toán cốt lõi (gộp thành 5 trong bài này):

  • ① Nghẽn I/O-bound trong TMĐT
  • ② Race Condition trong Flash Sale
  • ③+④ Nhất quán phân tán + Phân chia dòng tiền đa seller
  • ⑤ Authorization Gap trong AI Tool Calling
  • ⑥ Tìm kiếm tiếng Việt (ICU + BM25)

Related Work — Giới hạn của giải pháp truyền thống

Mỗi hướng truyền thống đều có một failure mode rõ ràng — đề tài chọn cách giải quyết tận gốc thay vì vá chồng.

Nghiệp vụ Giải pháp truyền thống Failure mode Cải tiến đề xuất
I/O-bound Spring MVC · Platform Threads · thread-per-request Thread starvation, latency amplification, connection pool cạn. Java 25 Virtual Threads + WebFlux
Race Condition Pessimistic lock DB · Optimistic retry Hot-row contention, retry storm, lock queue. Redis Lua Script (atomic Read-Check-Write)
Distributed Tx 2-Phase Commit · REST đồng bộ Blocking, cascading failure khi 1 node chết. Axon CQRS + Event Sourcing + Saga
Multi-vendor Money Merchant of Record · Đối soát cuối kỳ thủ công Không scale, vi phạm NĐ 101/2012, mở rộng PCI scope. Stripe Connect Express + Delayed Transfer 7 ngày
AI Authorization Direct Tool Calling (LLM gọi API trực tiếp) Confused deputy, prompt injection. Risk-Based Interceptor + Redis One-Time Token + HITL
Vietnamese Search SQL LIKE %kw% · Standard Analyzer Full table scan, sai biên từ ghép tiếng Việt. Elasticsearch ICU Analyzer + ICU Folding + BM25

📖CAP & Eventual Consistency

Gilbert & Lynch (2002) chứng minh strong consistency xuyên nhiều node thường hy sinh availability. Đề tài chọn Eventual Consistency + compensating transactions cho checkout.

📖JEP 444 — Virtual Threads

OpenJDK (2023): Virtual Threads là luồng siêu nhẹ do JVM quản lý, không ánh xạ 1:1 OS thread — giải quyết đúng root cause I/O-bound.

📖OWASP Top 10 LLM

OWASP (2025): LLM01 Prompt Injection là rủi ro #1. Human-in-the-loop + one-time token được chứng minh là baseline bảo vệ hữu hiệu.

Bài toán ①

1Concurrency I/O-Bound — Nghẽn cổ chai khi chờ

Logic nghiệp vụ đơn giản nhưng request phải chờ DB, Redis, Stripe, Elasticsearch → thread & connection pool cạn kiệt.

⚠️Define Problem

  • Thread-per-request giữ OS thread trong suốt thời gian chờ I/O.
  • Connection pool & thread pool bị chiếm giữ lâu → request mới xếp hàng dù CPU chưa quá tải.
  • Một service chậm (Stripe, DB) kéo p99 latency của toàn chuỗi checkout.

🛠️Technique áp dụng

Spring MVC + Java 25 Virtual Threads Spring WebFlux + Netty R2DBC Timeout / Bulkhead
  • Virtual Threads: JVM-managed, không 1:1 OS thread; khi chờ I/O → nhả carrier thread.
  • WebFlux cho gateway, SSE, chat, streaming — backpressure chống OOM.
  • R2DBC thay JDBC ở pipeline reactive; tránh block event loop.
  • Timeout + connection pool limit cho từng downstream — không để một nơi chậm kéo sập hệ thống.

🏗️Triển khai trong code

api-gateway (WebFlux + Netty) → identity / order / payment (MVC + Virtual Threads) → ai-chat / notification (WebFlux + SSE)

Ràng buộc kỹ thuật: tránh pinning trong synchronized / native call; không gọi JDBC blocking trong event loop; cấu hình timeout riêng cho từng downstream.

Kết quả: downstream chậm không làm thread pool cạn; service imperative vẫn lập trình tuần tự dễ đọc, dễ debug.

Bài toán ②

2Flash Sale — Mua nhanh nhưng không oversell

Hàng vạn request đọc–kiểm–ghi cùng một SKU trong giây đầu mở bán. Cần atomic trên in-memory store.

⚠️Define Problem

  • Read-Check-Write không nguyên tử → 2 request cùng đọc tồn kho = 1, cùng trừ → oversell.
  • Lock ở PostgreSQL tạo hot-row contention, hàng đợi khóa tăng theo cấp số nhân.
  • Optimistic retry gây retry storm khi tỷ lệ xung đột ghi quá cao.

🛠️Technique áp dụng

Redis Lua Script (EVAL/EVALSHA) Redis ZSET (lịch phiên) Lettuce / Netty client Kafka event downstream
  • Lua Script chạy nguyên tử trên 1 thread Redis → đóng gói Check-Limit-Decrement thành 1 critical section.
  • EVALSHA: gửi mã hash script đã load — payload cực nhỏ, throughput cao.
  • ZSET quản lý lịch phiên (start/end) chính xác hơn cron theo phút.
  • Sau khi quyết định mua → phát Kafka để order, product, search, notification đồng bộ bất đồng bộ.

🏗️Triển khai trong code

File product-service/config/RedisLuaConfig.java định nghĩa 2 Lua script nguyên tử:

STOCK_DECREMENT_LUA  -- KEYS[1] = stock:available:{variantId}, ARGV[1] = qty
  local cur = redis.call('GET', KEYS[1])
  if not cur then return -1 end            -- cache miss
  local n = tonumber(cur)
  local q = tonumber(ARGV[1])
  if n < q then return 0 end               -- insufficient
  redis.call('DECRBY', KEYS[1], q)
  return 1                                  -- success

STOCK_INCREMENT_LUA  -- dùng khi hủy / refund để trả kho
  return redis.call('INCRBY', KEYS[1], ARGV[1])

Flow nghiệp vụ: admin tạo phiên → buyer bấm mua → Lua script check + giữ kho tại Redis → phát order.checkout_submitted Kafka → order-service tạo parent + sub order → payment xử lý → confirm hoặc release reservation.

Kết quả: phản hồi SOLD_OUT/SUCCESS/LIMIT_EXCEEDED tức thì, 0% oversell, không đẩy tải xuống database giao dịch.

Bài toán ③ + ④ (gộp)

3Checkout phân tán & Dòng tiền đa seller

Một giỏ nhiều seller → một payment → nhiều transfer sau 7 ngày bảo vệ, đảm bảo audit & tuân thủ NĐ 101/2012/NĐ-CP.

⚠️Define Problem

  • Microservices có DB riêng → không thể dùng 1 transaction ACID cho Order ↔ Product ↔ Payment.
  • 2PC blocking giữ resource; Coordinator chết → resource bị kẹt vĩnh viễn.
  • Đối soát tiền thủ công cho hàng nghìn seller mỗi cuối kỳ — không scale, dễ sai sót.
  • Tự giữ tiền buyer rồi trả cho seller vi phạm luật trung gian thanh toán (NĐ 101/2012, NĐ 52/2024).

🛠️Technique áp dụng

Axon Framework (CQRS + Event Sourcing + Saga) Stripe Connect Express Delayed Transfer (7 ngày) Webhook HMAC-SHA256 ShedLock scheduled payout
  • Event Sourcing: lưu chuỗi event bất biến → audit 100% thay đổi trạng thái, replay khi cần.
  • Saga Orchestrator: state machine phối hợp reserve stock → create PaymentIntent → confirm; có compensating transaction tự động khi timeout (15 ph).
  • CQRS: tách command side (ghi) và query side (đọc) — query không ảnh hưởng command.
  • Stripe Connect: KYC/AML/PCI do Stripe xử lý; nền tảng giữ tiền ở Platform Account 7 ngày → Refund trực tiếp về thẻ buyer mà không cần transfer reversal (tránh số dư âm seller).
  • Webhook verify HMAC chống giả mạo; scheduled job quét payout đến hạn mỗi 5 phút.

🏗️Triển khai trong code

Order service: OrderProcessingSaga (Axon) với @DeadlineHandler cho payment-timeout 5 phút — tự động chuyển CANCELLED + phát Kafka event downstream.

Payment service: PayoutScheduler chạy cron 0 */5 * * * *, @SchedulerLock chống double-process; status RETURN_WINDOW → READY_FOR_PAYOUT → PAID_OUT đảm bảo idempotent. Gọi Transfer.create(...) với transfer_group + metadata.order_id; commission trừ theo platformFeePercentage.

Buyer Checkout → Saga: Reserve Stock → PaymentIntent (Stripe) → Webhook → Kafka → Order PAID
After 7 days → PayoutScheduler → Stripe Transfer → Seller Balance ↑ hoặc Refund → Buyer Card (trong 7 ngày)

Kết quả: eventual consistency ≤ 5s, audit trail 100%, không đối soát thủ công, không vi phạm pháp lý trung gian thanh toán, refund không làm seller âm số dư.

Bài toán ⑤

4AI Authorization Gap — LLM không đại diện cho ý chí người dùng

Tool Calling tiện lợi nhưng LLM chỉ suy luận ý định — không có consent có ý thức. Prompt Injection có thể ép LLM hủy đơn / hoàn tiền.

⚠️Define Problem

  • Confused deputy: LLM có quyền gọi API, nhưng quyết định chỉ dựa trên suy luận ngôn ngữ.
  • Prompt Injection gián tiếp: hacker nhúng lệnh vào mô tả sản phẩm → AI đọc và "nghe lời".
  • Không phân biệt tier rủi ro: đọc dữ liệu vs. hủy đơn vs. hoàn tiền.
  • Yêu cầu: mọi hành động State Change / Financial phải có Human-in-the-loop.

🛠️Technique áp dụng

Spring AI Tool Calling Risk-Based Interceptor Redis One-Time Token (TTL 5') SSE confirmation prompt MongoDB audit log
  • 3-tier risk classification: Read-Only (auto) / State Change (HITL) / Financial (HITL + token).
  • One-Time Token lưu Redis TTL 5 phút kèm ngữ cảnh (toolName, args, userId) — xóa ngay sau khi dùng (chống replay).
  • SSE đẩy confirmation prompt realtime tới UI; user click xác nhận mới thực thi.
  • Tool Call Logs + ownership check — AI thành "trợ lý đề xuất", không phải người tự quyết định.

🏗️Triển khai trong code

ChatActionService.executeConfirmedAction() thực hiện đúng flow:

if (actionType == "CANCEL_ORDER")   url = "/v1/orders/" + orderId + "/cancel";
if (actionType == "REQUEST_REFUND") url = "/v1/orders/parent/" + orderId + "/refund";

// WebClient gọi order-service kèm X-Access-Token + X-User-Id (ownership)
// → xác minh token trên Redis (findByIdAndUserId) → xóa token → gọi API
User: "Hủy đơn ORD-998" → LLM sinh tool call → Risk Interceptor (Tier 3) → Generate one-time token (Redis, 5') → SSE confirmation_required
User click Xác nhận → Validate & DELETE token → order-service.cancel() → SSE token stream + audit log

Kết quả: Read-Only tool chạy tự động; State Change & Financial bắt buộc HITL — AI chỉ đề xuất, người dùng thật sự ra quyết định.

5Vietnamese Search — Đúng ngữ nghĩa, đồng bộ gần realtime

Tiếng Việt có dấu thanh, từ ghép đa âm tiết, chuẩn Unicode không đồng nhất — cần ICU + read model riêng.

⚠️Define Problem

  • SQL LIKE %kw% → full table scan khi catalog lớn.
  • Standard Analyzer chia theo khoảng trắng → "máy tính" thành ["máy", "tính"], mất ngữ nghĩa từ ghép.
  • Unicode NFC vs NFD khác nhau giữa macOS / Windows / mobile → cùng từ nhưng không match.
  • User gõ không dấu ("may tinh") nhưng dữ liệu có dấu ("máy tính").

🛠️Technique áp dụng

Elasticsearch ICU Analyzer ICU Folding (lowercase + asciifolding) BM25 (k1=1.2, b=0.75) Kafka event-carried state transfer Idempotent consumer
  • icu_tokenizer: Unicode UAX #29 — phân tách đúng biên từ tiếng Việt.
  • icu_folding: "tài" → "tai" → match cả 2 dạng có/không dấu.
  • BM25 cân bằng tần suất + độ dài tài liệu + độ hiếm — phù hợp tiêu đề/mô tả sản phẩm.
  • Read model tách khỏi DB giao dịch: search-service consume Kafka event từ product-service → cập nhật index bất đồng bộ.
  • Alias-based reindex + ILM (4 phase: hot → warm → cold → delete) cho vòng đời index.

🏗️Triển khai trong code

EsIndexManager.createIndexAs() cấu hình analyzer tiếng Việt + BM25 similarity:

.analysis(a -> a.analyzer("vietnamese_analyzer", an -> an.custom(cu -> cu
        .tokenizer("icu_tokenizer")         // UAX #29 Unicode segmentation
        .filter("lowercase", "icu_folding") // "tài" → "tai", normalize Unicode
)))
.similarity("custom_bm25", sim -> sim.bm25(b -> b.k1(1.2).b(0.75)))

// Mapping: productName & productDescription dùng vietnamese_analyzer
// + sub-field ".keyword" cho exact match / sort / aggregation

Flow nghiệp vụ: product-service phát event (Created/Updated/Price/Stock/FlashSale) → Kafka → search-service consumers (ProductEventHandler, FlashSaleEventConsumer) → IdempotencyService chống duplicate → EsDocumentIndexer cập nhật ES → query path: ICU tokenize → BM25 rank → trả về < 50ms.

Kết quả: truy vấn "may tinh xach tay" ra đúng sản phẩm có dấu; search độc lập DB giao dịch; đồng bộ gần realtime; giảm tải DB chính.
