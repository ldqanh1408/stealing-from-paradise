## 1. System Overview

The FlashSale platform is a microservices-based e-commerce system deployed via Docker Compose on a self-hosted server. All public traffic enters through **Nginx** on port 80, which routes to internal services via the Docker bridge network.

### High-Level Architecture

```
                        ┌─────────────────────────────────┐
                        │         INTERNET                │
                        └──────────────┬──────────────────┘
                                       │
                                       │  HTTP :80
                                       ▼
              ┌────────────────────────────────────────────┐
              │            DEPLOY SERVER (VM)              │
              │                                            │
              │  ┌──────────────────────────────────────┐  │
              │  │  Docker Network: flashsale-net       │  │
              │  │                                      │  │
              │  │  ┌─────────────────┐                 │  │
              │  │  │  fs-reverse-    │ :80 (host)      │  │
              │  │  │  proxy (nginx)  │◄────────────────┼──┼─── PUBLIC ENTRY
              │  │  └────────┬────────┘                 │  │
              │  │           │                          │  │
              │  │           │ /api/* → fs-gateway:8080 │  │
              │  │           │ /seller/* → seller-app   │  │
              │  │           │ /admin/* → admin-app     │  │
              │  │           │ /* → customer-app        │  │
              │  │           ▼                          │  │
              │  │  ┌─────────────────┐                 │  │
              │  │  │  fs-gateway     │ :8080 internal  │  │
              │  │  │  (Spring Cloud) │ (NOT published) │  │
              │  │  └────────┬────────┘                 │  │
              │  │           │                          │  │
              │  │     ┌─────┴─────┬─────────┬─────┐    │  │
              │  │     ▼           ▼         ▼     ▼    │  │
              │  │  identity   payment  product order   │  │
              │  │  flashsale  search   notif   worker  │  │
              │  │                                      │  │
              │  │  ┌──────────────────────────────────┐│  │
              │  │  │ Infrastructure (PostgreSQL,      ││  │
              │  │  │ MongoDB, Redis, Kafka, Eureka)   ││  │
              │  │  └──────────────────────────────────┘│  │
              │  └──────────────────────────────────────┘  │
              │                                            │
              └────────────────────────────────────────────┘
```

### Key Design Principles

1. **Single public entry point**: Only Nginx is exposed to the host (port 80). All other services are internal-only.
2. **Service discovery via DNS**: Containers reach each other by service name (e.g., `fs-gateway:8080`) — Docker's embedded DNS resolves names on the network.
3. **No host port pollution**: Backend microservices never bind to host ports — they're only reachable via the gateway through Nginx.
4. **Environment-based config**: All container-specific values come from `.env.production` (generated by the deploy workflow).

## 2. Network Architecture

### Docker Network: `flashsale-net`

A user-defined bridge network that connects all containers. Defined in `docker-compose.yml`:

```yaml
networks:
  flashsale-net:
    name: flashsale-net
    driver: bridge
```

**Why a custom bridge network instead of the default `bridge`?**
- ✅ Containers can resolve each other by **service name** (e.g., `http://fs-gateway:8080`)
- ✅ Network isolation from other Docker projects on the same host
- ✅ Better security: only containers on this network can reach each other

### Container ↔ Service Mapping

| Service Name (compose) | Container Name | Internal DNS | Internal Port |
|------------------------|----------------|--------------|---------------|
| `reverse-proxy`        | `fs-reverse-proxy` | `fs-reverse-proxy` | 80 |
| `api-gateway`          | `fs-gateway`   | `fs-gateway` | 8080 |
| `identity-service`     | `fs-identity`  | `fs-identity` | 8081 |
| `payment-service`      | `fs-payment`   | `fs-payment` | 8082 |
| `order-service`        | `fs-order`     | `fs-order` | 8083 |
| `flashsale-service`    | `fs-flashsale` | `fs-flashsale` | 8084 |
| `product-service`      | `fs-product`   | `fs-product` | 8085 |
| `search-service`       | `fs-search`    | `fs-search` | 8086 |
| `notification-service` | `fs-notification` | `fs-notification` | 8087 |

## 3. Port Mapping

### Host-Exposed Ports (Production)

Only **two** ports are bound to the host in production:

| Host Port | Container | Purpose |
|-----------|-----------|---------|
| `80`      | `fs-reverse-proxy` (nginx) | Public web traffic |
| `8761`    | `fs-eureka` (discovery)    | Internal service registry monitoring (could be removed) |

> ⚠️ **API Gateway is NOT exposed on host port 8080 in production.**
> This was a deliberate change to eliminate the recurring port 8080 deployment conflicts. See `docs/deployment-port-8080-fix.md` for the full story.

### Development Mode (`docker-compose.yml` base)

For local development, the gateway IS bound to `127.0.0.1:8080` for direct API testing:

```yaml
api-gateway:
  ports: ["127.0.0.1:${PORT_GATEWAY:-8080}:8080"]
```

### Production Override (`docker-compose.prod-pulled.yml`)

In production, this binding is removed:

```yaml
api-gateway:
  ports: []          # No host bind
  expose:
    - "8080"          # Only internal network access
```

**Effect:**
- The gateway listens on port 8080 **inside** the container.
- Nothing on the host's network stack is bound to port 8080.
- Nginx reaches the gateway over the Docker network as `fs-gateway:8080`.

## 4. Nginx ↔ API Gateway Connection

This is the most critical link in the architecture. Here's how external requests reach internal microservices:

### ASCII Flow Diagram

```
    External Client                    Server (Host)                          Docker Network
    ───────────────                    ─────────────                          ──────────────

    curl http://my-domain.com/api/v1/products
            │
            │   1. TCP connect to port 80
            ▼
    ┌────────────────┐
    │  Internet      │
    │  (DNS resolves │
    │  to server IP) │
    └────────┬───────┘
             │
             │   2. Server receives on host:80
             ▼
    ┌─────────────────────────────────────────────┐
    │  Host network stack                         │
    │  (port 80 bound by Docker for fs-reverse-   │
    │   proxy container)                          │
    └─────────────────────┬───────────────────────┘
                          │
                          │   3. docker-proxy forwards to container
                          ▼
                   ┌─────────────────────────────────────┐
                   │  fs-reverse-proxy (nginx) container │
                   │  Listening on :80                   │
                   │                                     │
                   │  nginx.conf has:                    │
                   │    upstream gateway {               │
                   │      server fs-gateway:8080;        │
                   │    }                                │
                   │                                     │
                   │    location /api/ {                 │
                   │      proxy_pass http://gateway/...  │
                   │    }                                │
                   └────────────┬────────────────────────┘
                                │
                                │   4. nginx proxies to upstream
                                │      "fs-gateway" (DNS lookup
                                │      via Docker embedded DNS)
                                ▼
                   ┌─────────────────────────────────────┐
                   │  Docker bridge network              │
                   │  (flashsale-net)                    │
                   │  DNS: fs-gateway → 172.18.0.5       │
                   └────────────┬────────────────────────┘
                                │
                                │   5. TCP connect to 172.18.0.5:8080
                                ▼
                   ┌─────────────────────────────────────┐
                   │  fs-gateway (Spring Cloud Gateway)  │
                   │  Listening on :8080 (internal only) │
                   │                                     │
                   │  Routes to downstream microservices │
                   │  via Eureka service discovery       │
                   └────────────┬────────────────────────┘
                                │
                                │   6. Gateway calls e.g. fs-product:8085
                                ▼
                            (microservice handles request, returns response)
                                │
                                ▼
                            (response flows back through gateway → nginx → client)
```

### Configuration Pieces

**`docker-compose.yml`** (reverse-proxy service):

```yaml
reverse-proxy:
  build: ./nginx
  container_name: fs-reverse-proxy
  ports: ["${PORT_REVERSE_PROXY:-80}:${NGINX_PORT:-80}"]   # host 80 → container 80
  environment:
    - GATEWAY_HOST=fs-gateway      # ← Tells nginx which DNS to use
    - GATEWAY_PORT=8080            # ← Internal port
  networks: [flashsale-net]
  depends_on:
    api-gateway: { condition: service_started }
```

**`nginx/docker-entrypoint.sh`** (generates `/etc/nginx/conf.d/default.conf` at container start):

```nginx
upstream gateway {
    server fs-gateway:8080;     # ← Service-name DNS, resolved by Docker
}

location /api/ {
    limit_req zone=api_limit burst=20 nodelay;   # rate limit
    proxy_pass http://gateway/api/v1/;
}
```

**Why service-name DNS?**
- Container IPs are ephemeral (change on every restart)
- Service names are stable (defined in compose, never change)
- Docker's embedded DNS (`127.0.0.11`) handles resolution automatically

## 5. Docker Compose Structure

The deployment uses **two compose files layered together** via `-f`:

```bash
docker-compose \
  -f docker-compose.yml \              # base: dev defaults
  -f docker-compose.prod-pulled.yml \  # prod override: pulls images, removes ports
  --env-file .env.production \
  up -d
```

### Layering Diagram

```
┌─────────────────────────────────────────────┐
│  docker-compose.yml  (base — dev settings)  │
│                                             │
│  api-gateway:                               │
│    build: ./backend/api-gateway             │
│    container_name: fs-gateway               │
│    ports: ["127.0.0.1:8080:8080"]           │
│    healthcheck: ...                         │
│    depends_on: [eureka, postgres]           │
│    networks: [flashsale-net]                │
└──────────────────────┬──────────────────────┘
                       │
                       │   merged with ↓ (override takes precedence)
                       │
┌──────────────────────▼──────────────────────┐
│  docker-compose.prod-pulled.yml             │
│  (production override)                      │
│                                             │
│  api-gateway:                               │
│    image: ghcr.io/.../api-gateway:prod-...  │  ← replaces 'build:'
│    env_file: .env.production                │
│    ports: []                                │  ← REPLACES dev port mapping
│    expose: ["8080"]                         │
└─────────────────────────────────────────────┘

         RESULT (effective config):
┌─────────────────────────────────────────────┐
│  api-gateway:                               │
│    image: ghcr.io/.../api-gateway:prod-...  │ ← from override
│    container_name: fs-gateway               │ ← from base
│    ports: []                                │ ← from override (no host bind)
│    expose: ["8080"]                         │ ← from override
│    healthcheck: ...                         │ ← from base
│    depends_on: [eureka, postgres]           │ ← from base
│    networks: [flashsale-net]                │ ← from base
└─────────────────────────────────────────────┘
```

**Why layering?**
- Dev and prod share most config (network, healthcheck, dependencies)
- Only environment-specific values differ (image source, port exposure, env file)
- DRY: avoids duplicating 90% of the config in two files

## 6. CI/CD Deployment Pipeline

The `.github/workflows/deploy.yml` workflow handles the entire deploy. Triggered on:
- Push to `main` (production deploy)
- Push to `preview` (preview environment)
- Manual `workflow_dispatch`

│     ▼                                                               │

│     │                                                               │

│     │   Run health checks:                                          │

## 7. Request Flow

### Customer browses the storefront

```
Browser → http://server/
   ↓
nginx :80
   ↓ matches "location /"
   ↓ limit_req frontend_limit (20 req/s)
   ↓ proxy_pass http://customer-app/
   ↓
fs-customer-fe :3000
   ↓ serves React SPA bundle
   ↓
[browser renders, makes XHR calls]
```

### Customer places an order

```
Browser → http://server/api/v1/orders (POST)
   ↓
nginx :80
   ↓ matches "location /api/"
   ↓ limit_req api_limit (10 req/s)
   ↓ proxy_pass http://gateway/api/v1/orders
   ↓
fs-gateway :8080 (Spring Cloud Gateway)
   ↓ JWT validation
   ↓ rate limiting per user
   ↓ route lookup via Eureka
   ↓ /api/v1/orders → ORDER-SERVICE
   ↓
fs-order :8083
   ↓ writes to PostgreSQL
   ↓ publishes event to Kafka
   ↓ returns 201 Created
   ↓
[response flows back: fs-order → gateway → nginx → browser]
```

### Async order processing

```
fs-order publishes "order.created" → Kafka
                                       │
                                       ├──▶ fs-payment (charge card)
                                       ├──▶ fs-notification (email confirmation)
                                       ├──▶ fs-flashsale (update inventory)
                                       └──▶ fs-search (index new product state)
```

## 8. Health Checks

Three layers of health monitoring:

### 1. Container-level (`HEALTHCHECK` in Dockerfile / compose)

Docker periodically runs the healthcheck inside each container. If it fails enough times, container marked `unhealthy`:

```yaml
api-gateway:
  healthcheck:
    test: ["CMD-SHELL", "curl -f http://localhost:8080/actuator/health || exit 1"]
    interval: 30s
    timeout: 10s
    retries: 5
```

### 2. Service-level (Eureka)

Each microservice registers with Eureka and sends heartbeats. If a service stops sending heartbeats, Eureka removes it from the registry → gateway stops routing to it.

```
fs-gateway ──polls every 30s──▶ Eureka /eureka/apps
              ◀──returns active services list──
```

### 3. Deploy-time (workflow)

After `docker-compose up`, the workflow waits 60s then verifies:

```bash
# Internal (via SSH + docker exec)
docker exec fs-gateway curl http://localhost:8080/actuator/health

# External (nginx)
curl http://${SERVER_IP}/health
```

## 9. Common Operations

### View logs for a single service

```bash
ssh user@server
cd /opt/flashsale
docker-compose logs -f --tail=100 api-gateway
```

### Restart only the reverse-proxy (apply nginx config changes)

```bash
docker-compose restart reverse-proxy
```

### Pull new images and restart everything

```bash
docker-compose pull
docker-compose up -d
```

### Inspect what's reserving a host port

```bash
# Containers
docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'

# OS-level
sudo ss -tlnp | grep ':8080'
sudo lsof -i :8080
```

### Force-remove a stale container holding a port

```bash
docker rm -f <container-id>
```

### Generate a fresh `.env.production`

This is done automatically by the deploy workflow from GitHub Secrets. To manually regenerate, see Step 2 of the deploy script in `.github/workflows/deploy.yml`.

### Check Eureka for registered services

```bash
curl http://localhost:8761/eureka/apps
```

### Tail nginx access logs

```bash
docker exec fs-reverse-proxy tail -f /var/log/nginx/access.log
```
