# Spring Boot Profiles — How `application-dev.yml` and `application-prod.yml` Work

This document answers a very common question in this codebase:

> "Tôi thấy mỗi backend service có `application.yml`, `application-dev.yml`, `application-prod.yml` — nhưng tìm khắp code không thấy ai `import` hay gọi đến mấy file `-dev` / `-prod` đó. Vậy chúng được dùng ở đâu?"
>
> *"I see each backend service has `application.yml`, `application-dev.yml`, `application-prod.yml` — but searching the code I don't find anyone importing or calling those `-dev` / `-prod` files. Where are they used?"*

**Short answer**: Nobody calls them. Spring Boot loads them automatically based on the `SPRING_PROFILES_ACTIVE` environment variable. This is a built-in convention of the framework, not an explicit code reference.

## 1. The Mechanism: Spring Boot Profiles

Spring Boot has a built-in feature called **Profiles** that lets you maintain multiple sets of configuration in the same project, each tailored to a different environment (dev, staging, prod, test, etc.).

The framework follows **convention over configuration**:

- It looks at one specific environment variable: `SPRING_PROFILES_ACTIVE`
- Based on its value, it auto-loads files matching a specific naming pattern
- No imports, no `@Bean`, no Java code required

This is why you don't find any code "calling" `application-prod.yml` — Spring Boot's classpath scanner does it automatically at startup.

---

## 2. Naming Convention

Spring Boot looks for files in this exact pattern on the classpath:

| File | When Loaded | Purpose |
|------|-------------|---------|
| `application.yml` (or `.yaml`, `.properties`) | **Always** | Base/default configuration |
| `application-{profile}.yml` | Only when `{profile}` is active | Profile-specific overrides |

Example with `SPRING_PROFILES_ACTIVE=prod`:

```
backend/api-gateway/src/main/resources/
├── application.yml              ← LOADED (always)
├── application-prod.yml         ← LOADED (because active=prod)
└── application-dev.yml          ← NOT loaded
```

Example with `SPRING_PROFILES_ACTIVE=dev`:

```
backend/api-gateway/src/main/resources/
├── application.yml              ← LOADED (always)
├── application-dev.yml          ← LOADED (because active=dev)
└── application-prod.yml         ← NOT loaded
```

**Key rule**: Profile-specific values **override** base values. The base is the "default", profiles are "overlays".

## 3. How Profiles Are Activated

There are several ways Spring Boot determines which profile is active. In this codebase, we use the environment variable approach.

### Priority Order (highest to lowest)

1. Command-line argument: `--spring.profiles.active=prod`
2. JVM system property: `-Dspring.profiles.active=prod`
3. **Environment variable: `SPRING_PROFILES_ACTIVE=prod`** ← we use this
4. Value in `application.yml`: `spring.profiles.active: prod`
5. No profile (only `application.yml` loaded)

### Bootstrap Trick in `application.yml`

Look at `backend/flashsale-service/src/main/resources/application.yml`:

```yaml
spring:
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:dev}
```

Reading this line:

- `${SPRING_PROFILES_ACTIVE:dev}` — Spring's property syntax
- Means: "Read environment variable `SPRING_PROFILES_ACTIVE`. If unset, fall back to `dev`."

So:

| Env var value | Resolved profile |
|---------------|------------------|
| `SPRING_PROFILES_ACTIVE=prod` | `prod` |
| `SPRING_PROFILES_ACTIVE=dev` | `dev` |
| (unset) | `dev` (default) |

This makes local development "just work" — if you forget to set the env var, you get dev mode.

## 4. Full Flow: From `.env` to Spring Boot Config

The env variable doesn't magically appear inside the JVM. There's a chain of three layers that hands it off:

### Layer 1 — `.env` files (source of truth)

| File | Purpose | Generated by |
|------|---------|--------------|
| `.env.example` | Template, committed to git | Hand-written |
| `.env` | Local dev, gitignored | `cp .env.example .env` |
| `.env.production` | Production server, gitignored | `.github/workflows/deploy.yml` |

`.env.production` is generated fresh on every deploy by the deploy workflow (Step 2):
1. `cp .env.example .env.production` — copy the template
2. `sed -i` — inject secrets (from GitHub Secrets) into the copied template

```bash
# Simplified version of what deploy.yml does on the server:
cp "${PROJECT_DIR}/.env.example" "${PROJECT_DIR}/.env.production"

# Inject secrets via sed
sed -i 's|^JWT_SECRET=.*|JWT_SECRET='"${JWT_SECRET}"'|' "${PROJECT_DIR}/.env.production"
sed -i 's|^POSTGRES_PASSWORD=.*|POSTGRES_PASSWORD='"${POSTGRES_PASSWORD}"'|' "${PROJECT_DIR}/.env.production"
# ... (other secrets follow)

# Force production profile
sed -i 's|^SPRING_PROFILES_ACTIVE=.*|SPRING_PROFILES_ACTIVE=prod|' "${PROJECT_DIR}/.env.production"
```

The key insight: `.env.example` is the **single source of truth** for non-secret defaults. Secrets are never stored in any file on the server — they are injected at deploy time from GitHub Secrets.

### Layer 2 — `docker-compose` injects the env vars

In `docker-compose.yml`, every backend service has:

```yaml
api-gateway:
  env_file: .env       # ← reads ALL key=value pairs from .env
```

In production, `docker-compose.prod-pulled.yml` overrides this:

```yaml
api-gateway:
  env_file: .env.production    # ← uses production env file instead
```

When `docker-compose up` runs, every variable from the env file is injected into the container's environment as if you had run:

```bash
docker run -e SPRING_PROFILES_ACTIVE=prod -e JWT_SECRET=... <image>
```

### Layer 3 — Spring Boot reads it on startup

When the JVM starts inside the container:

1. Spring Boot scans the classpath for `application.yml`
2. Loads it
3. Looks at `spring.profiles.active`
4. Resolves `${SPRING_PROFILES_ACTIVE:dev}` against the OS environment
5. Sees `prod` → loads `application-prod.yml`
6. Merges base + profile config
7. Application starts with the merged config

## 6. Concrete Example: api-gateway

Real values from `backend/api-gateway/src/main/resources/`:

### `application.yml` (base — ALWAYS loaded)

```yaml
server:
  port: ${SERVER_PORT:8080}
spring:
  application:
    name: api-gateway
  cloud:
    gateway:
      httpclient:
        pool:
          maxConnections: 500       # ← default (good for dev)
        connect-timeout: 10000      # ← default (good for dev)
        response-timeout: 30s
```

### `application-prod.yml` (loaded ONLY when `SPRING_PROFILES_ACTIVE=prod`)

```yaml
spring:
  cloud:
    gateway:
      httpclient:
        pool:
          maxConnections: 1000      # ← OVERRIDE: prod needs more
        connect-timeout: 5000       # ← OVERRIDE: prod fails fast
        response-timeout: 10s       # ← OVERRIDE: prod is stricter

management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics

logging:
  level:
    root: INFO                      # prod uses INFO (no DEBUG noise)
    com.flashsale: INFO
    org.springframework.cloud.gateway: WARN
```

### Effective merged config when running with `SPRING_PROFILES_ACTIVE=prod`

```yaml
server:
  port: 8080                          # from base
spring:
  application:
    name: api-gateway                 # from base
  cloud:
    gateway:
      httpclient:
        pool:
          maxConnections: 1000        # from prod (overrides base's 500)
        connect-timeout: 5000         # from prod (overrides base's 10000)
        response-timeout: 10s         # from prod (overrides base's 30s)
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics  # only in prod
logging:
  level:
    root: INFO                        # only in prod
```

## 7. How Files Get Merged

Spring Boot uses a **deep merge** strategy:

- Profile-specific values **replace** matching keys in the base
- Keys not present in the profile file are **kept from the base**
- New keys added in the profile file are **added** to the merged config

Example:

```yaml
# application.yml
foo:
  a: 1
  b: 2
  c:
    nested: hello

# application-prod.yml
foo:
  b: 99      # override
  d: 4       # add new
  c:
    nested: world  # override
```

Result with `active=prod`:

```yaml
foo:
  a: 1                  # from base (untouched)
  b: 99                 # overridden by prod
  c:
    nested: world       # overridden by prod
  d: 4                  # added by prod
```

## 9. Common Pitfalls

### ❌ Forgetting to set `SPRING_PROFILES_ACTIVE`

**Symptom**: App starts in `dev` mode unexpectedly (e.g., loads seed data on production).

**Cause**: The fallback `${SPRING_PROFILES_ACTIVE:dev}` defaults to `dev`. If the env var isn't passed to the container, you accidentally run dev config.

**Fix**: Always verify the deploy workflow generates `.env.production` with `SPRING_PROFILES_ACTIVE=prod`.

### ❌ Renaming `application-dev.yml` to `dev-application.yml`

**Symptom**: Profile-specific config silently ignored.

**Cause**: Spring Boot only recognizes the **exact** pattern `application-{profile}.{ext}`. Any other naming is treated as an unrelated file.

**Fix**: Stick with `application-dev.yml`, `application-prod.yml`, `application-test.yml` etc.

### ❌ Putting profile-specific values in `application.yml`

**Symptom**: Production accidentally uses dev values (or vice versa).

**Cause**: Values in the base file are **always loaded**. They're only the default — you can't make them dev-only by putting them there.

**Fix**: Move dev-only values into `application-dev.yml`, prod-only values into `application-prod.yml`. Keep the base file for shared / default values.

### ❌ Multiple profiles active at once

You CAN do this:

```bash
SPRING_PROFILES_ACTIVE=prod,monitoring
```

This loads `application-prod.yml` AND `application-monitoring.yml`. The order of merging follows the order in the comma-separated list (later profiles override earlier ones).

We don't use this in the FlashSale platform — only single profile (`dev` or `prod`) — but it's worth knowing.

### ❌ Env var name typos

Spring Boot is case-sensitive on the property side:

- ✅ `SPRING_PROFILES_ACTIVE` (env var, uppercase + underscores) → resolves to `spring.profiles.active`
- ❌ `spring_profiles_active` (lowercase) — won't be picked up
- ❌ `SPRING.PROFILES.ACTIVE` (dots) — only valid in YAML/properties, not env

The env-var-to-property translation is automatic: dots → underscores, lowercase → uppercase.

## TL;DR

1. Spring Boot **automatically** loads `application-{profile}.yml` files based on the `SPRING_PROFILES_ACTIVE` env var. No code references needed.
2. Set `SPRING_PROFILES_ACTIVE=dev` in `.env` for local dev.
3. The deploy workflow auto-generates `.env.production` with `SPRING_PROFILES_ACTIVE=prod`.
4. `docker-compose` reads the env file via `env_file:` and injects the var into the container.
5. Spring Boot reads it at startup and merges base + profile config.
6. The "magic" is just Spring Boot's classpath naming convention — there's no explicit registration anywhere.
